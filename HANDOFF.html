1. 意思決定ログ

MCP vs CLI → MCP を選択
  • CLI + Skill + hooks 案も検討したが、以下の理由で MCP に決定：
  • マルチAI対応: Claude Code だけでなく Codex / Gemini でも使いたい。MCP ならプロトコル層で安全性が担保され、AI ごとに防御を書き直す必要がない
  • 業界標準: Claude / GPT / Gemini が MCP 対応に向かっている。エコシステムに乗る
  • 型安全: JSON Schema でパラメータを強制。存在しないツールは呼べない
フォーク vs 新規構築 → 新規構築
  • 既存 relation-mcp-server（Procrustes5）は個人開発でAPIカバー率が低い（3〜4割）
  • API自体がシンプルなREST（Bearer Token + JSON）なので新規構築のコストは低い
  • 既存実装は参考にするが、コードベースは独立させる
  • 将来的に C# ライブラリや CLI にも展開するため、API クライアント層を再利用可能な設計にする
派生プロダクトの展望
  • MCP サーバー（TypeScript）→ まずこれを作る
  • C# ライブラリ → MCP の API クライアント設計を参考に .NET 版を作成
  • CLI ツール → C# ライブラリを使って CLI 化（人間が直接叩く用途）
  • いずれも API 仕様は同一なので、MCP でエンドポイントを網羅しておけば他への展開はスムーズ

4. 安全性設計（ツール公開方針）

MCP の最大の利点：サーバー側でツールの公開/非公開を制御でき、どのAIクライアントが接続しても同じ安全性が保たれる。

推奨：3段階のツール公開レベル

レベル対象方針
READ 常時公開検索・一覧取得・チャット取得・添付DL制限なし公開。AI が自律的に使える
WRITE 確認付き公開コンタクト登録/更新、チケット更新、応対メモ作成、メール下書き、コメント公開するが、ツール説明に「確認を促す」記述を入れる
WRITE 非公開 or 要フラグコンタクト削除、メール送信、メール返信デフォルト非公開。設定で有効化する or 確認フラグ必須

マスタ管理系（MASTER）

チケット分類・ラベルの登録/更新はオプションツールとして実装。デフォルトは非公開。

レートリミット対策

60リクエスト/分。MCPサーバー内で X-RateLimit-Remaining を監視し、残り少ない場合は待機またはエラーを返す。

6. 派生プロダクト（C# ライブラリ / CLI）

MCP サーバーのAPI クライアント層の設計を、他言語へ移植しやすい構造にしておく。

展開計画

プロダクト言語用途優先度
MCP ServerTypeScriptAI ツール統合（Claude / Codex / Gemini）最優先
C# ライブラリC# / .NET自社システム連携、バッチ処理次フェーズ
CLI ツールC#（ライブラリ上に構築）運用者が直接叩く、スクリプト組み込み次フェーズ

設計のポイント

  • MCP の TypeScript 実装で、API クライアント部分（HTTP呼び出し + 型定義）と MCP ツール定義部分を分離する
  • API クライアント部分の仕様書 = このドキュメントのエンドポイント一覧がそのまま使える
  • C# 版は MCP の型定義（JSON Schema）を参考に、同等のリクエスト/レスポンス型を定義
